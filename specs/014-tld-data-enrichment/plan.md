# Implementation Plan: TLD Data Enrichment Engine

**Branch**: `014-tld-data-enrichment` | **Date**: 2026-07-30 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/014-tld-data-enrichment/spec.md`

## Summary

Build a reusable TLD checking engine (`lib/tld-checker/`) that queries NS + A records per TLD combination and persists results to the database. This is the server-capable shared engine — distinct from the standalone TLD Checker tool (Phases 14–15) which is browser-only. The engine has zero UI/database dependencies and can be called from Route Handlers, cron jobs, React hooks, or any Node.js context.

**Technical approach**: Generalize the existing DNS resolution engine (Phase 15 refactor) to support `type: "NS" | "A"`, then build the TLD-specific orchestration layer on top — parallel NS+A queries per TLD with concurrency control, root word extraction, and Supabase persistence with independent upserts.

## Technical Context

**Language/Version**: TypeScript 5.x strict mode

**Primary Dependencies**: Next.js 14+ App Router, Supabase PostgreSQL, Cloudflare DNS-over-HTTPS, existing `lib/dns/` shared engine (Phase 15)

**Storage**: Supabase PostgreSQL — `domain_extension_checks`, `tld_extensions`, `domains.reserved_tlds_count` / `domains.tlds_last_checked_at`. RLS on all tables.

**Testing**: Manual verification + `npx tsc --noEmit` type checking + SQL migration validation

**Target Platform**: Web (Vercel) — engine runs on both server (Route Handlers, cron) and client (React hooks, browser tools)

**Project Type**: Web application — reusable library module within a single Next.js app

**Performance Goals**: 10 TLDs checked in ≤ 10 seconds (20 DNS queries); persistence of 10 results in ≤ 2 seconds

**Constraints**: 15-TLD concurrency (30 HTTP requests). Browser: direct `fetch()` to DoH. Server: same `fetch()`. No API keys.

**Scale/Scope**: Engine covers 3 files (`types.ts`, `checkExtensions.ts`, `persistResults.ts`) + 1 utility (`rootExtractor.ts`). ~6 new Supabase query functions.
